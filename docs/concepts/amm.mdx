A ***commas*** token trades on its **[Meteora](https://www.meteora.ag) pool**: a Dynamic Bonding Curve at launch that Meteora migrates to a **DAMM v2** constant-product pool. The pool serves two jobs: it is the liquidity venue for longs (routed by Jupiter), and it produces the **mark price** that the [funding mechanism](/concepts/funding) compares against the oracle index.

## The pool holds SOL and the token

The Meteora pool is a constant-product pool over two real assets:

- SOL (lamports)
- the token (base units)

The pool is Meteora's audited infrastructure; commas holds no custody of it and no LP position for users to manage. The collectible is **not** an asset inside the pool: a constant-product AMM holds SOL and the token, never a physical card or NFT. "The underlying is the collectible" means the pool's token *is* the collectible's price (via the oracle index) and identity (via metadata), plus the optional [item swap](/concepts/synth-token#item-swaps) door, not a card sitting inside the pool.

## Swaps

Buys and sells route through **Jupiter** into the Meteora pool as standard constant-product swaps, with the pool's **0.7%** base fee taken on the trade. Fees are collected by Meteora and split 50/50 creator/protocol per the pool config; commas does not re-implement swap accounting. Pool trading neither mints nor burns supply.

## Spot and mark

The pool's spot price is expressed in lamports per whole unit (the same scale as the index). commas does not read spot directly, and it does not parse Meteora's pool bytes on chain. Instead the relayer computes the pool price from Meteora's public API and pushes it via [`push_mark`](/reference/instructions#push_mark); the program maintains `mark_ema`, a time-weighted EMA of the pushed mark, updated on every push and every funding crank:

```text
w  = mark_window_secs
dt = min(seconds since last mark update, w)

mark_ema = (mark_ema * (w - dt) + mark * dt) / w
```

<Warning>
This is the manipulation defense. A single-block push of the pool price moves `mark_ema` only by `dt / w`, and `dt` inside one block is zero or near zero. To move the mark meaningfully an attacker must hold the pool at a distorted price for a large fraction of the window, paying fees and inventory risk the whole time, while arbitrageurs trade against them. A bad `push_mark` from the oracle key can likewise only tilt the clamped funding flow, matching the trust already placed in that key for the index.
</Warning>

## What the mark does and does not touch

| Computation | Price used |
| --- | --- |
| Funding premium | `mark_ema` vs `index_twap` |
| Collateral ratio checks | index only |
| Liquidation eligibility and payouts | index only |

The mark's only job is steering funding. Collateral and liquidation math never read the pool, so manipulating the Meteora price cannot force anyone's liquidation. See [Price Index](/concepts/price-index) and [Liquidations](/concepts/liquidations).

## Venues

Every market carries a `venue` field. The shipped and current venue is **external**: the token launched on a **[Meteora](https://www.meteora.ag) Dynamic Bonding Curve** and trades in a **DAMM v2 pool**. The market attaches to the existing mint via [`create_external_market`](/reference/instructions#create_external_market), starts directly `Live`, and the mark is oracle-pushed. Liquidity lives in Meteora's audited, Jupiter-routed infrastructure; ***commas*** keeps the synthetic core (index, cash-settled shorts, funding, liquidations, item swaps).

<Note>
The **internal** venue (the program's own curve and AMM, with a preminted supply and an on-chain graduation gate) is the retired v1 design. It is superseded by the Meteora path above; new markets launch on Meteora.
</Note>

Two consequences of the external design:

- **Mark is oracle-pushed.** The program never parses external pool bytes on chain. The relayer computes the pool price from Meteora's public API and pushes it via `push_mark`; it lands in the `mark_ema` smoothing above.
- **The short side is cash-settled.** Shorts never draw tokens from a reserve. They post SOL collateral, and PnL settles in SOL against the index, with the [insurance fund](/concepts/insurance-fund) as the bounded counterparty. Total short open interest is capped by `max_open_interest`. See [Shorts](/concepts/shorts).
